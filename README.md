# at-include

Flatten `@<path>` Markdown imports the way [Claude Code](https://claude.com/claude-code)
inlines files referenced from a `CLAUDE.md` — as a standalone CLI you can run
anywhere: locally, in CI, or from a git hook.

Supported platforms: Linux (amd64, arm64), macOS (amd64, arm64), Windows (amd64).

## What it does

`at-include` reads a source file (default `AGENTS.src.md`), finds every
`@<path>` token that resolves to a real file relative to the file it appears
in, and replaces the token with that file's contents — recursively, so an
included file's own `@` imports are expanded too. The result is written to an
output file (default `AGENTS.md`) behind a generated-file banner. This lets
you author instructions across several small, reusable files and check in one
flattened, human- and agent-readable document.

Given `AGENTS.src.md`:

```markdown
# Project instructions

Please follow our coding conventions.

@notes.md
```

and `notes.md`:

```markdown
- Use tabs, not spaces.
- Write tests first.
```

running `at-include` produces `AGENTS.md`:

```markdown
> [!IMPORTANT]
> **This file is generated. Do not edit it directly — edits here will be
> overwritten.**
>
> Edit [`AGENTS.src.md`](AGENTS.src.md) instead, then regenerate:
> `at-include --src AGENTS.src.md --out AGENTS.md`
>
> **If you are an agent** and were asked to change `AGENTS.md`, make the change
> in `AGENTS.src.md` and regenerate — do not edit this file.

# Project instructions

Please follow our coding conventions.

Contents of notes.md (project instructions, checked into the codebase):

- Use tabs, not spaces.
- Write tests first.
```

## The `@path` rules

| Token | Behavior |
|---|---|
| `@notes.md` where `notes.md` exists (relative to the **importing file's** directory, or as an absolute path) | Expanded: replaced with the file's contents, recursively |
| `@nope.md` where the path doesn't exist | Left literal — never an error |
| `@some-dir` where the path is a directory, not a regular file | Left literal — never an error |
| `foo@bar.com` (email) | Left literal — never scanned as an import |
| `@scope/package` (npm-style package mention) | Left literal unless a file with that literal path actually exists |
| `` `@notes.md` `` inside an inline code span | Never expanded — code spans are passed through verbatim |
| `@notes.md` inside a fenced code block | Never expanded — fenced blocks are skipped entirely, delimiters and all |
| Any file, once expanded | Inlined **at most once**. A second reference to the same file (including a cycle back-edge) prints `Contents of <path> (already inlined above):` instead of re-inlining — this is what makes cycles terminate instead of looping forever |

The output is always: the generated-file banner, a blank line, the flattened
content, ending in exactly one trailing newline.

## Install with mise (recommended)

[mise](https://mise.jdx.dev) is a polyglot version manager. Pinning
`at-include` through it in your repo's `mise.toml` means CI, git hooks, and
every developer on the team run the **exact same binary version** — no global
install, no "works on my machine" drift, and no separate step to keep a
Homebrew/npm-installed copy in sync with what CI expects.

Add it to your repo's `mise.toml`. `at-include` isn't (yet) in mise's central
tool registry, so pin it with the explicit `github:` backend, which installs
directly from GitHub Releases:

```toml
[tools]
"github:happycollision/at-include" = "latest"  # pin to an exact version once you've picked one, e.g. "0.1.0"
```

Then install and lock it:

```sh
mise install
mise lock
```

Commit both `mise.toml` and the resulting `mise.lock`. From then on, anyone
(or any CI runner) who runs `mise install` in this repo gets the identical
`at-include` binary.

> **Note on availability:** `at-include` has no tagged release yet, so `mise
> install` can't resolve the entry above today — verified: it 404s against
> GitHub's releases API. The `github:` form is otherwise the correct,
> verified syntax for a repo with no separate mise-registry entry (confirmed
> against a real published tool, `github:BurntSushi/ripgrep`); it will work
> unmodified for `at-include` as soon as a tagged release exists. Until then,
> use one of the alternatives below.

### Alternatives

Install directly with Go (requires a Go toolchain):

```sh
go install github.com/happycollision/at-include/cmd/at-include@latest
```

Or download a release archive directly from the
[Releases page](https://github.com/happycollision/at-include/releases) —
`at-include_<version>_<os>_<arch>.tar.gz` (`.zip` on Windows), plus a
`checksums.txt` to verify it — and put the extracted binary on your `PATH`.

## Usage

```
Usage: at-include [options]

Flatten @<path> Markdown imports, the way Claude Code inlines files referenced
from a CLAUDE.md. Reads a source file, replaces every @<path> that resolves to a
real file with that file's contents (recursively), and writes the result.

Options:
  (no args)           Generate and write the output file
  --check             Verify the output file is up to date; exit nonzero if not
  --src <path>        Source file (default: AGENTS.src.md)
  --out <path>        Output file (default: AGENTS.md)
  --root <path>       Root for marker paths (default: the source file's directory)
  --max-depth <n>     Error if a resolved import chain exceeds n hops
  --marker-desc <s>   Override the text in "Contents of X (<s>):"
  --list-imports      Print the @path candidates found in the source, one per line
  --version           Print the version
  --help, -h          Show this help

Exit codes: 0 success, 1 out-of-date or runtime error, 2 usage error.
```

`--out` may never resolve to the same file as `--src` — at-include refuses to
run rather than risk overwriting your hand-authored source.

## Use it as CI tooling

`--check` is the star here: it regenerates the output in memory, compares it
to what's on disk, and exits nonzero (without touching your working tree) if
they differ. That's exactly what a CI gate needs — "did someone edit
`AGENTS.src.md` without regenerating `AGENTS.md`?"

Add tasks to the consumer repo's `mise.toml`:

```toml
[tools]
"github:happycollision/at-include" = "latest"  # pin to an exact version, e.g. "0.1.0"

[tasks.agents-build]
description = "Regenerate AGENTS.md from AGENTS.src.md"
run = "at-include"

[tasks.agents-check]
description = "Verify AGENTS.md is up to date (CI gate)"
run = "at-include --check"
```

Then, in a GitHub Actions workflow, install the pinned toolchain with
[`jdx/mise-action`](https://github.com/jdx/mise-action) and run the task:

```yaml
- uses: jdx/mise-action@v2
  with:
    install: true

- name: Verify AGENTS.md is up to date
  run: mise run agents-check
```

Because `mise-action` reads `mise.toml`/`mise.lock`, this installs the exact
`at-include` version your team pinned — the CI check runs the same binary a
developer would run locally.

## Add it to a git hook

If a change to `AGENTS.src.md` lands without a matching `AGENTS.md`, it's
better to catch that before it's committed. **Only do this if you have a
clean, shared way to manage git hooks in your project** — a hand-rolled
`.git/hooks/pre-commit` script works locally but lives outside version
control, so it silently doesn't apply to any other clone or teammate.

### lefthook (recommended)

[lefthook](https://github.com/evilmartians/lefthook) stores hook
configuration in a checked-in `lefthook.yml`, and is itself easy to pin via
mise (`at-include`'s own repo dogfoods exactly this setup — see this
project's [`lefthook.yml`](lefthook.yml)). Add it alongside `at-include`:

```toml
[tools]
"github:happycollision/at-include" = "latest"
lefthook = "latest"
```

```yaml
# lefthook.yml
pre-commit:
  jobs:
    - name: agents-build
      glob: "AGENTS.src.md"
      run: at-include
      stage_fixed: true
```

`stage_fixed: true` is what makes this pleasant rather than annoying: instead
of failing the commit because `AGENTS.md` is stale, lefthook runs
`at-include`, then stages the regenerated `AGENTS.md` so it joins the same
commit automatically. Each developer runs `mise exec -- lefthook install`
once after cloning (this writes into the untracked `.git/hooks/` directory,
so it can't be skipped by checking out the repo alone).

### pre-commit framework (alternative)

If your project already standardizes on the Python
[pre-commit](https://pre-commit.com) framework instead, a local hook entry in
`.pre-commit-config.yaml` gets you the same result:

```yaml
repos:
  - repo: local
    hooks:
      - id: at-include
        name: Regenerate AGENTS.md
        entry: at-include
        language: system
        files: ^AGENTS\.src\.md$
```

(The pre-commit framework doesn't have lefthook's `stage_fixed` auto-restage
behavior for a `language: system` hook — if `at-include` regenerates
`AGENTS.md`, pre-commit will report the hook as having modified files, and
you'll need to `git add AGENTS.md` and re-run `git commit`.)

### Keep `--check` in CI regardless

A git hook is a convenience, not a guarantee — anyone can bypass one with
`git commit --no-verify`. Keep `--check` running as a required CI job (see
[Use it as CI tooling](#use-it-as-ci-tooling) above) even if you've also wired
up a hook.

## Development

```sh
mise install       # install the pinned Go toolchain and tools
mise run test       # run the unit tests and the fixture CLI suite
mise run check      # what CI runs: format check, lint, and tests
```

The black-box CLI test suite lives under [`test/`](test/README.md); the case
directories in [`test/cases/`](test/cases) are plain data (a `cmd` file, an
input `files/` tree, and `expect/*` files) — adding a test case means adding a
directory, not writing Go.
